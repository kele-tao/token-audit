# Architecture

```
src/token_audit/
  tokenizer.py   BPE replay from a committed merge table + pre-tokenizer port
  pricing.py     pricing snapshot loader, all cost arithmetic
  loader.py      file walker, markdown/JSON/JSONL parsers -> Documents
  models.py      dataclasses: Segment, Document, Finding, ScanResult
  detectors.py   eight waste detectors + MinHash helpers
  optimize.py    pure text transforms and the change ledger
  scanner.py     orchestration: load, count, detect, project
  report.py      terminal / markdown / JSON / HTML renderers
  accuracy.py    golden-set measurement
  budget.py      plan parser and projection
  cli.py         argument parsing, exit codes, friendly errors
  data/          merge tables, pricing snapshot, packaged golden set
```

## Data flow

1. `scanner.collect_documents` walks the target with
   `loader.iter_source_files` (junk directories are skipped) and turns each file
   into a `Document` of `Segment`s. Segments carry a kind and a line number so a
   finding can point at a line rather than a file.
2. A `Counter` wraps a `BPETokenizer` and memoises counts per string. Detectors
   share one counter, so repeated text is counted once.
3. `detectors.run_detectors` calls every detector, sorts findings by monthly
   saving and returns them. Detectors never mutate documents.
4. `scanner.scan` builds the cost table by calling `pricing.cost_per_calls` once
   per model with the average per-file token count.
5. Renderers are pure functions of `ScanResult`; nothing renders while scanning,
   which is what makes the HTML deterministic.

## The tokenizer

The vendored file is an LZMA stream containing:

```
"TAV1" | varint vocab_size | 256 bytes (byte rank order) | varint left, right * n
```

Ranks 0-255 are single bytes. Every later rank is the merge of two earlier
ranks, so the vocabulary is reconstructed into `bytes -> rank` at load time.
Encoding is the standard loop: start from the bytes of the pre-tokenizer piece,
repeatedly merge the adjacent pair with the lowest rank, stop when no pair is in
the table.

The pre-tokenizer is a port of the published cl100k and o200k regexes written
with explicit Unicode ranges (generated from `unicodedata` at import time,
cached in the module) rather than property escapes, because Python's `re` module
does not support `\p{L}`. ASCII-only text uses a faster equivalent pattern.

## Why the golden set is committed

`tests/data/golden_tokens.json` holds 200 (text, cl100k count, o200k count)
triples generated by the reference implementation with a fixed seed, plus a copy
inside the package so an installed wheel can self-check. Without it, "our counts
are accurate" would be an unverifiable claim; with it, `token-audit accuracy` is a
one-line experiment a reviewer can run.
